## Root cause found and fixed

Your log (`~/VRITRA_GCS_logs/vritra_gcs.log`) showed the real problem:

```
File "threading.py", line 1233, in is_alive
File "threading.py", line 1171, in _wait_for_tstate_lock
TypeError: 'Event' object is not callable
```

All three of your worker threads — `SerialLink`, `GsGnssLink`, `Simulator` — stored their stop flag as `self._stop = threading.Event()`. Problem: `threading.Thread` itself has a **private method called `_stop()`** that CPython calls internally to finalize a thread. Assigning `self._stop = Event()` silently overwrites that method. Once the thread actually exits (port lost, reconnect, etc.), the next `is_alive()` call — which your UI calls every tick in `_update_chips()` — tries to invoke `self._stop()` and blows up because it's now an `Event`, not a function.

This matches your log exactly: `COM6` disconnected → thread died → every subsequent `is_alive()` check threw → the "chips" status panel silently failed (caught by `_safe()`) → the app looked like it couldn't reconnect/report connection state correctly, and `_toggle_link()`'s own `is_alive()` checks could throw too, corrupting the connect/disconnect toggle logic.

**Fix applied**: renamed `self._stop` → `self._stop_evt` in all three thread classes (15 sites) in [vritra_gcs.py](vritra_gcs.py). Recompiled clean.
